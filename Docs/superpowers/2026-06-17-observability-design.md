RECOMMENDATION for the distributed-tracing+metrics pillar: do NOT adopt OpenTelemetry. OTel's BatchSpanProcessor relies on a background worker thread that Cloud Run's between-request CPU throttling breaks (spans buffer and can't flush), and the Cloud-Run-supported SimpleSpanProcessor exports each span synchronously in-band — adding a blocking Cloud Trace API call to every request and hitting Trace API rate limits. Both conflict with the project's HARD no-worker + minimal-overhead constraints, and OTel adds ~6-10 deps to a deliberately lean stack. Instead: implement lightweight manual trace-context propagation in code — parse the X-Cloud-Trace-Context header Cloud Run already injects, bind trace_id/request_id to a contextvars ContextVar in a new TraceContextMiddleware, emit structured JSON logs to stdout with Cloud Logging's native special fields (severity, logging.googleapis.com/trace), and one structured access-log line per request carrying latency + DB-query count/time (via connection.execute_wrapper, which works with DEBUG=False). Tag Sentry events with the same trace_id for cross-tool correlation. Emit domain-metric log lines at the existing choke-points (content-tier decisions, age-gate blocks, registration outcomes, verification attempts, throttle hits). Derive ALL metrics (p50/p95/p99 latency, error rate, 4xx/5xx-by-route, DB pressure, throttle/registration/age-gate counts) as Cloud Logging log-based metrics in the console — zero extra infra, no Cloud Monitoring custom-metrics API, no new runtime dependencies at all. This gives trace<->log<->Sentry correlation for free on Cloud Run while honoring every hard constraint.
