# JokesFor MVP Launch — Master Plan

> Single source of truth for the launch-gating work. Supersedes the frozen `.planning/STATE.md` / `ROADMAP.md` (original 12-phase search-engine plan). Reflects the shipped JokesForPeople pivot + the Rich-Media & Compliance Addendum scope as of 2026-06-15.

**Detailed TDD steps for Wave 0 live in** `2026-06-15-prod-integrity-fixes.md`. The compliance work-streams below are scoped with file maps + decisions; they become no-placeholder TDD plans once the decisions in §Decisions are locked.

**Total effort:** ~22-28 dev-days for the recommended MVP across all three waves. Wave 0 ~6-8 days (celery S ~0.5d, hardening M ~2-3d, gcs M ~1.5-2d, unmock M ~1.5-2d — the unmock is frontend and can run fully in parallel with the three backend items). Wave 1 ~14-18 days (shared Firebase gate S ~0.5-1d, coppa L ~6-8d, legal L ~4-6d code, gdpr M ~2.5d — coppa and legal/gdpr can overlap once the Firebase gate lands). Wave 2 ~4-6 days (moderation M). EXCLUDES three explicitly-deferred XL/external efforts NOT counted here: the full FTC verifiable-parental-consent vendor flow + parental dashboard (coppa, multi-week), the legal-copy counsel review (external calendar long-pole, runs parallel to Wave 1 code), and DSA/DMCA notice-and-action (moderation, post-UGC). Legally-launchable text-only MVP is reached at the END of Wave 1; Wave 0 is pure de-risking and Wave 2 is post-launch-acceptable.

**Overview:** Eight work-streams sequence into three waves plus a cross-cutting integrity preflight. WAVE 0 (prod-integrity, no decisions, de-risks everything): celery removal, hardening (shared throttle cache + security headers + SECRET_KEY guard + /healthz + Sentry), GCS media storage, and the frontend un-mock. These have zero load-bearing design decisions, are independently shippable, and each closes a live production gap (throttle bypass, ephemeral media loss, mocks in prod). WAVE 1 (launch-gating compliance — App-Store + GDPR/COPPA block submission): COPPA age gate + content_tier serving lock, legal pages + consent banner, and GDPR export/delete. These are the legal launch gate. WAVE 2 (pre-UGC, deferrable): moderation report/block UI + enforcement + admin triage — App-Store-minimum but only truly load-bearing once the catalog is less admin-curated; it can trail the legal gate by days. The single most important cross-stream finding: Firebase Analytics auto-inits at app boot (main.tsx L5 `import './lib/firebase'`, verified) BEFORE any consent or age check — this is simultaneously the coppa-stream D4 and the legal-stream D4. It is ONE fix, not two, and it is the highest-severity live violation (children's + non-consented data collection happening right now). It must be done once, early in Wave 1, and both compliance streams consume it. Second key finding: content_tier exists on the model but is enforced in ZERO serving paths (grep of views/managers/recommendations returned nothing) — under-18 and anonymous children can currently receive tier_2/tier_3 content everywhere; this is the COPPA stream's real exposure and the true critical-path item, heavier than the DOB UX. Total recommended-MVP effort ~22-28 dev-days (Wave 0 ~6-8d, Wave 1 ~14-18d, Wave 2 ~4-6d), with the legal-copy counsel review running in parallel as an external long-pole that gates Wave 1 completion regardless of code velocity.

1. celery (clean baseline, slim settings/requirements) — S

3. SHARED Firebase analytics gate (remove eager init, initAnalytics(), default OFF — the one cross-stream dependency, consumed by both coppa and legal) — S
4. coppa content_tier serving lock (the actual live legal exposure: tier filtering at all read paths) — heaviest single item, L
5. coppa DOB age gate + null-DOB safe-default + flag rollout — part of L
6. legal pages + consent banner code (consumes Firebase gate) AND counsel review of copy (external long-pole running in parallel) — L
7. gdpr export + delete (depends on GCS settled for avatar purge) — M
8. => legally-launchable text-only MVP reached at end of Wave 1; moderation (Wave 2) is NOT on the launch critical path

## Decisions required (lock these before the compliance plans become executable)

### CD1 — Firebase Analytics gating — how and when to stop the eager boot-time init (this is BOTH coppa-D4 and legal-D4; deduped into one decision)

**Recommendation:** Do it ONCE, first in Wave 1, as a shared building block both compliance streams consume. Remove `import './lib/firebase'` from main.tsx (verified L5), expose initAnalytics(), default OFF. The legal ConsentBanner calls initAnalytics() only on accept-non-essential; the coppa Kids-Mode/anonymous/under-18 path never calls it. This is the single highest-severity live violation (children's + non-consented data collection happening now) and the only true cross-stream code dependency — sequencing it twice would conflict and waste effort.

**Blocks:** Blocks BOTH the coppa zero-data Kids Mode and the legal consent banner; nothing else in either stream can be called compliant until this lands. It is the gate item for all of Wave 1's frontend compliance.

### CD2 — Where does age/DOB data live, and how much COPPA do we build for launch (coppa D1 + D2 + D3)

**Recommendation:** DOB on UserProfile (existing OneToOne on the verified default auth.User — NOT a custom AUTH_USER_MODEL swap, which is the most expensive post-launch Django migration). For launch: BLOCK under-13 at signup with a neutral DOB gate and DEFER the full FTC verifiable-parental-consent vendor flow (multi-week, external). Kids Mode = anonymous/session zero-data tier_1-only browsing + automatic tier_1 lock for any signed-in under-18. This is exactly the Addendum's prescribed Phase-1 path and collects no child data at all.

**Blocks:** Blocks the registration DOB field/serializer, the migration, and the Children's-Privacy page copy (which must claim no-knowing-under-13-collection consistently with the actual block). Gates legal launch.

### CD3 — How is content_tier enforced in serving (coppa D5 + D6)

**Recommendation:** Add ONE allowed_tiers(request) resolver and apply it at ALL read paths: JokeViewSet.get_queryset, the random action, JokeManager.search, and recommendations.get_personalized_joke. Rule: anon/Kids-Mode/under-18/null-DOB -> {tier_1}; adults -> {tier_1, tier_2} with explicit opt-in; tier_3 never served. Treat null DOB as age-unknown -> tier_1 safe default. This is the actual live exposure (verified: content_tier is enforced in zero paths today) and is reused by Kids Mode and moderation framing — build the chokepoint once, DRY and auditable.

**Blocks:** Blocks the legally-launchable claim outright — until this ships, minors and anonymous children receive tier_2/tier_3 on every read path. It is the true critical-path compliance item, ahead of the DOB UX.

### CD4 — Consent banner granularity + storage (legal D2 + D3)

**Recommendation:** Simple Accept / Reject (essential-only), stored localStorage-only as a versioned record {version, analytics, ts}. There is exactly one non-essential tracker (Firebase) and consent must work pre-login for anonymous visitors, so category toggles and backend persistence are overshoot (YAGNI). Re-prompt when the version bumps; classify httpOnly auth/JWT cookies as strictly-necessary/exempt in the copy.

**Blocks:** Blocks the ConsentBanner implementation and its wiring to the shared Firebase gate (CD1). Gates GDPR/ePrivacy compliance for launch.

### CD5 — Who authors and signs off the legal copy, and how is it rendered (legal D1 + D5)

**Recommendation:** Counsel-reviewed templated docs authored into typed TSX/TS content modules under src/content/legal (no MDX/markdown tooling — none installed, unjustified for 4 docs). Engineer drafts from reputable templates with a DRAFT/version marker; counsel reviews and signs off before production. START the counsel track in parallel on day one of Wave 1 — it is the external long-pole that gates the wave regardless of code velocity. Shipping engineer-written placeholders to prod is the one legally-risky option.

**Blocks:** Blocks the legal stream's completion (not its code scaffolding). The counsel review, not the engineering, is the gating risk for the Wave 1 legal item.

### CD6 — Account-deletion semantics + re-auth (gdpr D1 + D2 + D3 + D4)

**Recommendation:** Synchronous in-request zipped-JSON export (no worker/flag/email — per-user data is small). Confirmed HARD delete: require re-auth (current password; typed confirmation string for Google-only accounts with no usable password), then inside a transaction delete the avatar file from the live storage backend, purge EmailMessageLog rows by user_id and matching to_email (PII that survives the SET_NULL cascade), blacklist refresh tokens, and user.delete() to cascade all owned rows. No anonymize-and-retain tier. Depends on GCS being settled (Wave 0) so the avatar purge hits a real blob.

**Blocks:** Blocks the GDPR launch-gate item. The GCS dependency means GDPR cannot be declared complete until Wave 0's storage work lands.

### CD7 — Moderation scope + block enforcement + report dedup/throttle (moderation D1 + D2 + D4 + D5)

**Recommendation:** Block enforcement = filter TopJokestersView only, behind a reusable blocked_user_ids(user) helper (jokes have no author FK — verified — so content-feed filtering is a no-op). Use admin actions on the existing ContentReport.status + resolved_at for triage (no new ModerationAction/audit model). Add a 'report' ScopedRateThrottle (~10/hour) reusing the verified verification_resend pattern, and decide report dedup (soft 'already reported' vs unique_together migration). DEFER DSA notice-and-action, appeals, and DMCA to post-UGC. This is the deferrable Wave 2 item; build the App-Store minimum only.

**Blocks:** Blocks broadening to real UGC, NOT the text-only launch. Can trail the Wave 1 legal gate by days; benefits from CD3's allowed_tiers resolver and the hardening throttle substrate but neither is a hard blocker.

# Wave 1 — Launch-gating compliance (scoped)

## COPPA 2025 Kids Mode + Neutral Age Gate — Scope & Design Decisions

LAUNCH-BLOCKING compliance work. The app targets kids 6-12 but currently collects ZERO age data: registration is email+password only (EmailOnlyRegisterSerializer), there is no DOB/age/COPPA field anywhere, and the Joke.content_tier field (tier_1/2/3) exists but is NEVER used in any serving filter, queryset, manager.search, random endpoint, or recommendations.py — it is admin-decoration only. Frontend Firebase Analytics is LIVE (src/lib/firebase.ts calls getAnalytics(), imported globally in main.tsx), which directly violates Kids Mode zero-data. The Addendum (read in full) mandates: neutral server-side DOB entry (not yes/no), verifiable parental consent for under-13, under-18 locked to Tier 1, and a zero-data Kids Mode. The Addendum itself names the YAGNI MVP path: 'the simplest COPPA-compliant approach for Phase 1 is a separate Kids Mode that collects zero personal data; this eliminates most COPPA obligations.' RECOMMENDED MVP: (1) store DOB on UserProfile (NOT a custom AUTH_USER_MODEL swap — far cheaper migration on the default auth.User), (2) BLOCK under-13 at signup with a neutral DOB gate (defer the full FTC verifiable-parental-consent flow — it is a multi-week vendor integration), (3) wire content_tier into serving so under-18 is locked to tier_1 (closes the real exposure gap and is reused by Kids Mode), (4) gate Firebase init behind a Kids-Mode-off check + anonymous neutral age gate before any third-party SDK loads. This blocks the legally dangerous case (children's data collection) without building the heaviest piece. Everything is request-triggered; no Celery/cron needed.

**Effort:** L — ~6-8 dev-days for the recommended MVP (block-under-13 + neutral DOB gate + content_tier serving lock + Firebase analytics gating + tests). Breakdown: backend DOB/migration ~0.5d, registration gate ~0.5d, content_tier enforcement across 4 read paths + search/recs ~1.5d, null-DOB/legacy handling ~0.5d, backend tests ~1d, frontend DOB UX + types ~1d, Firebase analytics gating + Kids-Mode tier-1 shell ~1d, integration/e2e + flag rollout ~0.5d. EXCLUDES the full FTC verifiable-parental-consent flow + parental dashboard (deferred per D2) — that is a separate XL (multi-week, vendor-dependent) effort.

**Satisfies:** Addendum §2.2 COPPA Deep Dive — 'Neutral Age Gate: at signup present a neutral age verification (e.g. Enter your date of birth) that does not coach the user to lie. If under 13, trigger COPPA flow.' (drives D7, D2); Addendum §2.2 — 'Verifiable Parental Consent: for under-13 users implement one of the FTC-approved consent methods (credit card, gov ID, video call, KBA, face-match ID).' (deferred per D2); Addendum §2.2 — 'Data Minimization for Kids: no analytics tracking, no advertising IDs, no geolocation for under-13.' (drives D4 Firebase gating); Addendum §2.2 Practical Approach for MVP — 'the simplest COPPA-compliant approach for Phase 1: a separate Kids Mode that collects zero personal data beyond a parent-created account credential. No analytics, no third-party SDKs, no device identifiers. This eliminates most COPPA obligations.' (validates the recommended YAGNI path; drives D3/D4); Addendum 'Age Verification' summary row — 'Birth date on profile. Under-18 cannot view labeled content.' **Decisions:**

- **[D1] Where is DOB stored: UserProfile vs custom AUTH_USER_MODEL vs separate AgeVerification model?**
  - Options: Add date_of_birth to UserProfile (existing OneToOne, L430); Introduce a custom AUTH_USER_MODEL with DOB; Create a separate AgeVerification model (1:1 to User)
  - → **Rec:** Add date_of_birth to UserProfile. — _The project uses the DEFAULT django auth.User (confirmed: no AUTH_USER_MODEL in settings). Swapping to a custom user model post-launch is the single most expensive/risky Django migration (must be done before first migrate ideally; retrofitting requires recreating the user table, repointing every FK/migration, and a data move) — pure overshoot for one date field, violates YAGNI. UserProfile already exists, is auto-created by signal, and holds privacy fields, so DOB belongs there with zero new table. A separate AgeVerification model only earns its keep once you store consent artifacts (parental-consent receipts, verification-method, timestamps) — defer it to the parental-consent phase, not MVP._
- **[D2] Under-13 handling for MVP: block registration vs build the full verifiable-parental-consent flow?**
  - Options: Block under-13 at signup (neutral message); Build full FTC verifiable parental consent (credit card / gov ID / face-match); Allow under-13 into a credential-only Kids Mode now
  - → **Rec:** Block under-13 at signup for launch; defer full parental-consent flow. — _The Addendum itself prescribes this as the Phase-1 path ('simplest COPPA-compliant approach... eliminates most COPPA obligations'). Verifiable parental consent requires integrating an FTC-approved vendor (credit-card, gov-ID, or face-match) — a multi-week, paid, externally-dependent build that also pulls in the parental dashboard, consent-revocation, and child-data-deletion obligations. Blocking under-13 means we collect no child data at all, which is the safest possible COPPA posture and unblocks launch now. The neutral DOB gate + tier-locking we build is the foundation the consent flow plugs into later._
- **[D3] Is Kids Mode a separate authenticated experience, an anonymous mode, or just the under-18 tier-lock?**
  - Options: Kids Mode = anonymous/session zero-data browsing of tier_1 only (no account); Kids Mode = an account-scoped flag on UserProfile; Kids Mode = just the automatic under-18 tier_1 lock (no distinct mode)
  - → **Rec:** MVP Kids Mode = anonymous/session, zero-data, tier_1-only browsing (no account, no analytics) PLUS automatic tier_1 lock for any signed-in under-18 user. — _Because under-13 cannot create accounts (D2), the genuinely child-facing surface is anonymous browsing. The Addendum says tier_1 ('Bucket 3') is 'freely viewable by all users, including children in Kids Mode, anonymous web visitors, and search-engine crawlers'. So Kids Mode is really: serve only tier_1 + load zero third-party SDKs for anon/kids sessions. No new account concept needed for MVP — it reuses the tier filter (D6) and the analytics gate (D4). An explicit account-scoped kids flag is overshoot until parental accounts exist._
- **[D4] How does Kids Mode suppress Firebase Analytics and any third-party SDKs (zero-data)?**
  - Options: Conditionally initialize Firebase only for confirmed-adult, non-kids sessions; Keep Firebase global but disable analytics collection at runtime; Remove Firebase entirely
  - → **Rec:** Make Firebase/analytics init conditional — never call getAnalytics() until a neutral age gate is satisfied AND the session is not Kids Mode; default to OFF. — _src/lib/firebase.ts currently calls getAnalytics() at module load and main.tsx imports it globally (side-effect import), so EVERY visitor — including anonymous children and crawlers — loads Google Analytics before any age check. That is a direct COPPA violation for the kids/anon surface. Runtime 'disable collection' is insufficient because the SDK still loads and can set identifiers. The fix is to gate initialization: export initAnalytics() and call it only for confirmed-adult sessions. Don't rip Firebase out (it may host non-analytics features) — just stop auto-initializing analytics._
- **[D5] How are existing users and null-DOB rows treated after the migration?**
  - Options: Treat null DOB as age-unknown → safest tier (tier_1 only) until they provide DOB; Treat null DOB as adult (grandfather existing users); Force a DOB-collection interstitial on next login for null-DOB users
  - → **Rec:** Treat null DOB as age-unknown and serve the safe (tier_1) default; prompt for DOB on next login via a non-blocking interstitial. — _Defaulting unknown-age users to adult re-opens the exact exposure COPPA penalizes ($53,088/violation). Safe-by-default (tier_1) means a missing DOB can never leak tier_2/tier_3 content. A soft interstitial lets real adults restore full access without a hard lockout. This matches the email-verification rollout philosophy already in the repo (gate behind a flag, fail safe)._

## GDPR Data Export + Safe Account Deletion (synchronous, no-worker)

Both endpoints are stubs today: UserAccountDeleteView (jokes/views.py L1618-1626) does a bare user.delete() with no confirmation/re-auth and no media/log handling; DataExportView (L1629-1638) returns a static 202 "being prepared" placeholder that never produces a file. Both are wired in jokes/urls.py L70-71 (DELETE/GET /api/v1/users/me/ and /api/v1/users/me/data-export/).

Findings that shape the design: (1) There is NO custom user model — it is django.contrib.auth.User; allauth EmailAddress/SocialAccount and notifications.EmailVerification cascade off the user FK, EmailMessageLog.user is SET_NULL (keeps to_email), ShareEvent.user is SET_NULL (anonymizes), JokePack.created_by / JokeSubmission.published_joke are SET_NULL. So a plain user.delete() ALREADY cascades all 20+ user-owned rows (SavedJoke, Collection, Favorite, JokeRating, JokeReaction, DailyJoke, Streak, StreakDay, JokeView, JokeSubmission, ContentReport, UserBlock both directions, UserVibe, MysteryBoxRoll, JokePackProgress, UserPreference M2M, UserProfile, UserAchievement, EmailVerification) — what is MISSING is a confirmation/re-auth gate, refresh-token blacklisting, deletion of the user's avatar file, and an explicit purge of EmailMessageLog rows (which otherwise survive with to_email retained — a GDPR Art.17 gap). (2) STORAGES default is local FileSystemStorage in committed settings — no GCS backend wired in the repo; the only user-owned media is UserProfile.avatar (Joke.share_image is platform-owned). (3) token_blacklist app is installed, so we can blacklist the refresh cookie on delete. (4) Scale is small (per-user rows in the hundreds, single Neon Postgres), so a synchronous in-request JSON-zip export streamed as an HttpResponse is well within Cloud Run request limits and fully honors the NO-Celery/NO-worker principle.

Recommendation (MVP, YAGNI): (A) Export = synchronous in-request build of a single JSON document serialized from the user's rows, returned as an application/zip HttpResponse attachment (one data.json inside) with Content-Disposition; no worker, no flag, no email. (B) Deletion = confirmed HARD delete: require a re-auth confirmation in the request body (current password, or for Google-only accounts a typed "DELETE"/email-match confirmation since they have no usable password), then run user.delete() inside a transaction, explicitly delete the avatar file, explicitly delete EmailMessageLog rows for that user/email, and blacklist the refresh token. No anonymize-and-retain tier for MVP.

**Effort:** M — ~2.5 days (export shape + zip ~0.75d, deletion helper + re-auth + token/cookie handling ~1d, tests for both ~0.75d). No migrations, no new dependencies (zipfile, token_blacklist, transaction all already available).

**Satisfies:** GDPR Art.15 (right of access — export includes all categories of personal data held); GDPR Art.17 (right to erasure — hard delete + EmailMessageLog/to_email purge + avatar file deletion); GDPR Art.20 (data portability — structured, machine-readable JSON in a zip); App Store Review Guideline 5.1.1(v) (in-app account deletion with confirmation); Compliance Addendum (COPPA/GDPR/DSA scope added to MVP per project memory)

- **[D3] Confirmation / re-auth step before deletion?**
  - Options: Require current password in the DELETE body (re-auth); Require a typed confirmation string only; No confirmation — rely on the authenticated session
  - → **Rec:** Require re-auth: password for password accounts, typed confirmation string for Google-only accounts (user.has_usable_password() == False) — _Hard delete is irreversible, so a confirmation gate is mandatory to prevent accidental/CSRF-driven deletion. Password re-auth is the standard bar. Google-OAuth-only users have no usable password (has_usable_password() is False), so for them we accept a typed confirmation (e.g. their email or the literal word DELETE) — this keeps the single endpoint working for both auth paths without forcing a password set._
- **[D4] Does deletion also purge EmailMessageLog and stored media?**
  - Options: Purge both: delete EmailMessageLog rows for the user/email and delete the avatar file from storage; Purge media only; keep email logs for audit; Purge neither (current behavior)
  - → **Rec:** Purge both EmailMessageLog (by user_id and matching to_email) and the UserProfile.avatar file — _EmailMessageLog.to_email is PII and survives the cascade via SET_NULL — leaving it violates Art.17, so it must be explicitly deleted. # Wave 2 — Pre-UGC (deferrable, not on launch critical path)

## Moderation MVP: Report/Block UI + Block Enforcement + Admin Triage

Backend ContentReport and UserBlock models, endpoints (POST /reports/, POST|DELETE /users/{id}/block/), serializer, and read-only admin already exist and are sound. Three gaps remain, all closable to the App-Store minimum without DSA/AI scope: (1) NO frontend UI to report a joke or block a user; (2) blocks are stored but NEVER enforced in any query; (3) admin can view reports but has no triage action (status is editable as a plain field, with no resolved_at stamping or workflow).

A defining fact from the code: jokes are admin-curated and the Joke model has NO author/creator FK (jokes/models.py L96-155). So "report" targets a joke regardless of authorship, and "block" has almost nothing to filter on the content side. The only place a blockable user's identity is exposed to other users today is TopJokestersView (jokes/views.py L1521, ranks users by published submissions, AllowAny). Reaction endpoints (views.py L399-421) return only aggregate counts plus the requester's own reaction — no other-user identity — so there is nothing there to filter. JokeReaction/JokeRating/SavedJoke are all private-to-self surfaces.

Recommended scope (App-Store minimum, YAGNI): wire a ReportDialog + Block control on the frontend to the EXISTING endpoints; add a thin block-enforcement layer that (a) hides blocked users from TopJokestersView and (b) makes the block list self-consistent (blocked users can't appear in any future attribution surface via one reusable helper); add an admin triage action (Mark reviewed/resolved/dismissed) that stamps resolved_at. Add a ScopedRateThrottle on /reports/ mirroring the existing verification_resend pattern. Defer DSA notice-and-action, appeals, DMCA counter-notice, and any ModerationAction/audit-log model to the pre-UGC wave — they are not App-Store gating for a text-only admin-curated catalog.

**Effort:** M — 4 to 6 days. Backend enforcement + throttle + admin actions + tests ~2 days; frontend ReportDialog + block wiring + hooks + tests ~2-3 days. No new models if dedup is handled softly (add ~0.5 day if a unique_together migration is chosen).

**Satisfies:** App-Store: in-app mechanism to report objectionable content (ReportDialog wired to POST /reports/); App-Store: in-app mechanism to block abusive users (Block control wired to POST/DELETE /users/{id}/block/ + enforcement in TopJokesters); App-Store: a means to act on reports (admin triage actions stamping resolved_at); DSA notice-and-action / statements-of-reasons / appeals — DEFERRED to pre-UGC wave; DMCA counter-notice — DEFERRED to pre-UGC wave; Compliance Addendum: content moderation surface (Phase 1 text-only, admin-curated; AI screening + rich-media CSAM explicitly OUT)
