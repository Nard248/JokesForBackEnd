# MVP 0.2 — Demo Slice 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use `- [ ]`.

**Goal:** Ship one read-only backend endpoint GET /api/v1/creators/me/insights/?period= in a new creator_insights app, plus a frontend Creator Insights dashboard page wired into the existing CreatorHub. All metrics computed on-read from existing engagement events via the JokeSubmission.user->published_joke attribution join. No migrations on the jokes tables, no worker/cron, owner-scoped reads bypass the content-tier serving lock. TDD throughout: Django runner on local Postgres for backend, vitest for frontend.

**Architecture:** New modular app creator_insights mirroring the notifications app boundary (own apps/models/services/serializers/views/urls/throttles/permissions/tests; FKs only to AUTH_USER_MODEL; reads jokes models read-only). models.py is empty for this slice (zero new tables). services.build_creator_insights(creator, period) is the single pure-function entry point returning a plain dict; resolve_creator_jokes(creator) isolates the attribution join so a future Joke.creator FK is a one-line swap. CreatorInsightsView(APIView, IsAuthenticated+IsCreator) serializes it. Mounted at /api/v1/creators/ alongside the existing jokes/notifications includes. Owner-scoped: the joke resolver does NOT apply the tier gate (creator sees own tier_2); response contains no other user's identity. Frontend: features/creator-insights/api.ts (react-query hook) + lib/api.ts client/types + pages/CreatorInsightsPage.tsx, routed at /create/insights under ProtectedRoute and linked from CreatorHub.
