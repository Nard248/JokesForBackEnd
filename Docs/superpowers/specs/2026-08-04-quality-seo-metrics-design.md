# Quality, SEO & Metrics — Design (2026-08-04)

A three-workstream initiative to take JokesFor from "feature-complete, deployed" to
"launch-quality": faster and observable, discoverable by search/social, and guarded by
standing CI + security tooling. Approved by owner 2026-08-04. Executed autonomously
(subagent-driven, adversarial review per task), with all prod-gated actions surfaced for
owner approval rather than performed.

Prod-gated items (surfaced, NOT auto-applied): backend deploy (push→Cloud Build),
frontend deploy (push→Firebase), `min-instances` change, GCP log-based metric + dashboard
creation, enabling Dependabot/Actions in repo settings, Google Search Console verification.

---

## Workstream 1 — Metrics & Performance ("Fix + measure")

**Problem.** Sustained single-client probing of prod shows `/api/v1/jokes/` (the feed —
highest-traffic read once launched) at **p50 ~2.0s / p95 ~2.2s**, while every other read is
~0.5s. `min-instances=0` also gives a 10–14s cold-start tail. No p95/p99 dashboard exists,
though per-request `latency_ms` is already logged per route to Cloud Logging.

**1a. Fix the feed query.**
- Profile the jokes list viewset locally (reproduce with `assertNumQueries` / query logging;
  the access-log middleware already records query count + time per request).
- Root-cause is expected to be N+1 serialization and/or missing `select_related`/
  `prefetch_related` on related rows (format, age_rating, language, media, taxonomies,
  author, per-viewer annotations), and/or a missing index. Fix the queryset + serializer;
  add an index only if EXPLAIN warrants it.
- Regression guard: a test asserting the list endpoint issues a bounded, constant number of
  queries regardless of page size (kills N+1 permanently).

**1b. p95/p99 observability.**
- Define a **Cloud Logging log-based distribution metric** over the `jokesfor.access`
  `latency_ms` field, labelled by `route`, plus a **Cloud Monitoring dashboard** (per-route
  p50/p95/p99, request count, error rate). Deliver as versioned `gcloud` commands +
  dashboard JSON committed to the repo (`ops/monitoring/`). Apply via gcloud if access
  permits; otherwise the owner runs the one-liners.

**1c. Cold starts.**
- Prepare `gcloud run services update jokesforbackend --region us-east1 --min-instances=1`
  with a cost note. **Owner-gated — teed up, not applied.**

**Deliverable state:** feed fix merged + deployed (gated push); dashboard/metric defined and
applied-or-teed-up; min-instances teed up.

## Workstream 2 — SEO ("Full, done right" — no framework rewrite)

**Problem.** The frontend is a client-rendered SPA with a bare `index.html`: title only, no
meta description, no Open Graph/Twitter, no `robots.txt`/`sitemap.xml`, no structured data,
no prerendering. Crawlers and (critically) non-JS social scrapers see an empty shell for
every dynamic page. Backend already generates OG share cards that nothing surfaces.

**2a. Per-route meta.** Add `react-helmet-async`; wrap the app in `HelmetProvider`. Static
defaults in `index.html` (description, OG, Twitter, theme-color, canonical) + per-route
`<Helmet>` on Landing, Creator profile, and Joke detail — the Joke/Creator OG image points at
the **existing backend share card**.

**2b. Crawl basics.** `public/robots.txt` (allow, reference sitemap). A **dynamic
`sitemap.xml`** generated by the backend from published, non-removed, tier_1 jokes + public
creators, served on the frontend domain via a Firebase Hosting rewrite to Cloud Run so it
stays fresh. (Alternative considered: build-time static sitemap — rejected as stale between
infrequent deploys.)

**2c. Structured data.** JSON-LD (schema.org) via Helmet: `CreativeWork`/`SocialMediaPosting`
on jokes, `ProfilePage`/`Person` on creators, `WebSite` + `Organization` on landing.

**2d. Prerender.**
- Static/marketing routes (landing, about, legal): **build-time prerender** via `react-snap`
  so non-JS crawlers get real HTML with zero new infra.
- Dynamic content routes (`/jokes/:id`, `/creators/:id`): **dynamic rendering for bots** —
  Firebase Hosting detects known bot UAs and rewrites to a backend endpoint that returns a
  meta-correct HTML shell (title/description/OG/JSON-LD from the joke/creator + share card),
  which real users never hit. Scalable social-scraper support without SSR.
- **Phasing:** 2a–2c + static prerender first (the high-ROI 80%, no new infra); bot-rendering
  for content routes second. Owner flagged they may stop after phase 1 — checkpoint there.

**Deliverable state:** meta/helmet/robots/sitemap/JSON-LD/static-prerender merged + deployed
(gated FE push, + BE sitemap endpoint); bot-rendering built or explicitly deferred; owner
does Search Console verification + sitemap submission.

## Workstream 3 — Maintenance & Quality ("Standing infra + audit")

**Problem.** Backend has **no CI** (804 tests run only manually; nothing gates a bad commit).
Frontend CI is Firebase-deploy only. No lint enforcement on backend, no dependency or
security scanning anywhere.

**3a. CI that gates.**
- Backend: GitHub Actions running the full Django suite against a Postgres service container
  on push/PR (`DATABASE_URL=` `DB_PASSWORD=` pattern), + `manage.py check`.
- Frontend: Actions running `npm test -- --run` + `npm run build` + lint on PR.

**3b. Lint/format.** Backend: `ruff` (lint) + `black` (format) via `pyproject.toml`, enforced
in CI. Frontend: keep ESLint, add Prettier; enforced in CI.

**3c. Security & deps.** Dependabot config (both repos), `pip-audit` + `bandit` (backend) and
`npm audit` (frontend) in CI (audit non-blocking initially → report, then ratchet).

**3d. One-time cleanup.** Fix violations the new linters/scanners surface, remove dead code,
address real security findings. **Timeboxed** — no sprawling refactors; formatting-only diffs
land in a single isolated commit so they don't obscure logic changes.

**Deliverable state:** CI green on both repos; linters/scanners wired; cleanup landed; owner
enables Dependabot/Actions permissions in repo settings.

---

## Sequencing & execution

1. **Workstream 1** (feed fix + observability) — self-contained, continues the perf thread.
2. **Workstream 3** (CI/lint/scan) — safety net established *before* the large SEO changes.
3. **Workstream 2** (SEO) — largest build, lands gated by the new CI.

Each workstream: build → test → adversarial review → fix → whole-branch review, on its own
branch, merged to main and deployed only on owner approval. Ledger: `.superpowers/sdd/progress.md`.
